# مختبر 11 - إدارة هوية العملاء واتحاد هويات المؤسسات متعددة المستأجرين (Keycloak CIAM)

## ما يثبته هذا المختبر

يقوم تسجيل الدخول الموحد للقوى العاملة بربط الموظفين الداخليين بالتطبيقات السحابية. في المقابل، يربط اتحاد هوية البرمجيات كخدمة متعددة المستأجرين (Multi-Tenant SaaS) آلاف مزودي الهوية المؤسسيين الخارجيين في منصة تطبيق موحدة مع فرض العزل التام بين المستأجرين.

يقوم هذا المختبر بإعداد مركز اتحاد هويات مؤسسي متكامل في Keycloak: ستضبط ميزة اكتشاف النطاق الأصلي (HRD) لتوجيه بريد `user@acme.com` إلى مزود SAML مؤسسي وبريد `user@globex.com` إلى مزود OIDC مؤسسي، وتوفير سجلات المستأجرين عند أول تسجيل دخول، وتوليد رموز JWT تحتوي على معرّف المستأجر (`tenant_id`) لعزل قواعد البيانات.

## المعمارية

```
[المتصفح / المستخدم]
       │
       ▼ (1. إدخال البريد الإلكتروني: user@acme.com)
[بوابة تسجيل الدخول (نطاق: saas-platform)]
       │
       ▼ (2. التوجيه التلقائي عبر النطاق @acme.com)
[مزود هوية شركة Acme] (SAML 2.0)
       │
       ▼ (3. تأكيد SAML بالبريد والمجموعات)
[وسيط اتحاد هويات Keycloak]
       │
       ▼ (4. إصدار رمز JWT يحمل tenant_id="acme")
[الخادم الخلفي لتطبيق SaaS] (التحقق من الرمز وعزل المستأجر)
```

## المتطلبات الأساسية

- تشغيل Docker Desktop محلياً.
- تشغيل Keycloak 24+ محلياً.
- توفر أدوات `curl` و`jq`.

## الخطوة 1 - تشغيل Keycloak في Docker

```bash
docker run -d --name keycloak-ciam \
  -p 8080:8080 \
  -e KEYCLOAK_ADMIN=admin \
  -e KEYCLOAK_ADMIN_PASSWORD=AdminPassword123! \
  quay.io/keycloak/keycloak:latest start-dev
```

## الخطوة 2 - إنشاء نطاق SaaS وعميل التطبيق

1. افتح لوحة التحكم `http://localhost:8080/admin` وسجل الدخول باستخدام `admin` / `AdminPassword123!`.
2. أنشئ نطاقاً جديداً باسم `saas-platform`.
3. أنشئ عميلاً جديداً باسم `cloud-app` بنوع OpenID Connect، وفعل خاصية المصادقة السرية (Confidential Client) مع ضبط الروابط المقبولة `http://localhost:3000/*`.

## الخطوة 3 - إعداد مزودي الهوية للمستأجرين

- **المستأجر A (شركة Acme)**: أضف مزود SAML باسم `acme-idp` واضبط النطاق التابع `@acme.com`.
- **المستأجر B (شركة Globex)**: أضف مزود OIDC باسم `globex-idp` واضبط النطاق التابع `@globex.com`.

## الخطوة 4 - ضبط تدفق اكتشاف النطاق الأصلي (HRD)

1. في قسم **Authentication**، انسخ التدفق الافتراضي وسمه `multi-tenant-browser`.
2. أضف خطوة **Home Realm Identifier** واضبط مطابقة النطاقات (`acme.com` -> `acme-idp` و`globex.com` -> `globex-idp`).
3. عيّن التدفق الجديد كتدفق تصفح افتراضي للنطاق.

## الخطوة 5 - تضمين معرّف المستأجر في رموز الوصول

أضف معرّف سمة مخصصة (Token Mapper) للعميل `cloud-app`:
- اسم السمة والادعاء: `tenant_id`
- النوع: `String`
- تفعيل الإضافة إلى ID Token وAccess Token.

## الخطوة 6 - التحقق واختبار الرموز

عند استبدال رمز التفويض، افحص رمز JWT للتأكد من احتوائه على معرّف المستأجر:
```json
{
  "iss": "http://localhost:8080/realms/saas-platform",
  "sub": "b8f2409c-d079-4d81-8172-120091823901",
  "email": "testuser@acme.com",
  "tenant_id": "org_acme_corp",
  "azp": "cloud-app"
}
```
يضمن هذا الادعاء قيام الخادم الخلفي للتطبيق بإلحاق شرط `WHERE tenant_id = 'org_acme_corp'` على كافة استعلامات قواعد البيانات، مانعاً أي تداخل في البيانات بين المستأجرين.
