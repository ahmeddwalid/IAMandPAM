# تعمق في تبادل رموز OAuth 2.0 (RFC 8693)

## ما الذي يحله تبادل الرموز

تبادل رموز OAuth 2.0 (RFC 8693) يسمح للعميل بتبادل رمز بآخر. هذا مطلوب عندما:

- خدمة تحتاج لاستدعاء خدمة أخرى نيابة عن المستخدم (تفويض).
- خدمة تحتاج للتصرف كمستخدم (انتحال هوية).
- رمز يحتاج إلى تبادله برمز بنطاقات أو جمهور مختلف.
- رمز يحتاج إلى تحديث أو تجديد.

بدون تبادل الرموز، كل خدمة ستحتاج بيانات اعتماد المستخدم أو رمزًا منفصلًا لكل خدمة لاحقة.

## طلب تبادل الرمز

تبادل الرموز يستخدم نقطة نهاية الرمز القياسية لـ OAuth 2.0 مع نوع منح خاص:

```http
POST /token HTTP/1.1
Host: idp.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=eyJhbGciOiJSUzI1NiIs...
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&requested_token_type=urn:ietf:params:oauth:token-type:access_token
&audience=https://api.downstream.example.com
&scope=read write
```

المعاملات الرئيسية:
- `grant_type`: يجب أن يكون `urn:ietf:params:oauth:grant-type:token-exchange`.
- `subject_token`: الرمز المراد تبادله.
- `subject_token_type`: نوع رمز الموضوع (مثل رمز وصول، JWT، تأكيد SAML).
- `requested_token_type`: نوع الرمز المطلوب (مثل رمز وصول، رمز تحديث).
- `audience`: الجمهور المقصود للرمز الجديد.
- `scope`: النطاقات المطلوبة للرمز الجديد.

## التفويض مقابل انتحال الهوية

### التفويض

التفويض يعني أن الخدمة اللاحقة تتصرف نيابة عن المستخدم، لكن هوية المستخدم محفوظة. الرمز الجديد يحتوي على هوية المستخدم وهوية الممثل.

```json
{
  "sub": "user-123",
  "act": {
    "sub": "service-a"
  },
  "aud": "https://api.downstream.example.com",
  "scope": "read write"
}
```

مطالبة `act` (الممثل) تحدد الخدمة التي طلبت الرمز. مطالبة `sub` (الموضوع) تحدد المستخدم.

### انتحال الهوية

انتحال الهوية يعني أن الخدمة اللاحقة تتصرف كمستخدم، دون مطالبة ممثل. الرمز الجديد يحتوي على هوية المستخدم فقط.

```json
{
  "sub": "user-123",
  "aud": "https://api.downstream.example.com",
  "scope": "read write"
}
```

انتحال الهوية أكثر خطورة: الخدمة اللاحقة لديها وصول كامل كمستخدم، دون طريقة للتمييز بين الطلب المنتحل والطلب المباشر.

### متى تستخدم كلًا منهما

- **التفويض**: استخدمه عندما تحتاج الخدمة اللاحقة للتصرف نيابة عن المستخدم ولكن هوية المستخدم يجب أن تكون محفوظة للتدقيق.
- **انتحال الهوية**: استخدمه عندما تحتاج الخدمة اللاحقة وصولًا كاملًا كمستخدم والتدقيق ليس مصدر قلق. نادرًا ما يُنصح به.

## سلاسل رموز الممثل

في بنية متعددة الخدمات، تبادل الرموز يمكن أن يخلق سلاسل: الخدمة A تتبادل رمزًا للخدمة B، الخدمة B تتبادل للخدمة C، وهكذا. كل تبادل يضيف مطالبة `act` إلى الرمز.

```json
{
  "sub": "user-123",
  "act": {
    "sub": "service-a",
    "act": {
      "sub": "service-b"
    }
  },
  "aud": "https://api.service-c.example.com"
}
```

مطالبة `act` متداخلة: كل طبقة تمثل خدمة في السلسلة. سلسلة `act` في الرمز تُظهر مسار التفويض الكامل.

### حدود عمق السلسلة

السلاسل العميقة تزيد من حجم الرمز وتعقيده. أفضل ممارسة: حدّد عمق السلسلة بـ 3-5 مستويات. إذا تجاوزت السلسلة هذا الحد، يجب أن يفشل تبادل الرمز.

## أنماط عبر السحابة

تبادل الرموز يتيح اتحاد الهوية عبر السحابة: رمز صدر من مزوّد سحابة واحد يمكن تبادله برمز من مزوّد سحابة آخر.

### تبادل الرموز من AWS إلى GCP

1. المستخدم يصادق إلى AWS STS ويستلم رمز وصول AWS.
2. العميل يتبادل رمز AWS برمز GCP عبر خدمة تبادل الرموز.
3. رمز GCP يستخدم للوصول إلى موارد GCP.

### تبادل الرموز من Azure إلى AWS

1. المستخدم يصادق إلى Entra ID ويستلم رمز Entra ID.
2. العميل يتبادل رمز Entra ID برمز AWS عبر خدمة تبادل الرموز.
3. رمز AWS يستخدم لافتراض دور AWS.

### خدمة تبادل الرموز

خدمة تبادل الرموز هي وسيط موثوق يتحقق من الرمز المصدر ويصدر رمزًا هدفًا:

```python
def exchange_token(source_token, target_audience):
    # Validate the source token
    claims = validate_jwt(source_token)
    
    # Create the target token
    target_token = create_jwt({
        "sub": claims["sub"],
        "aud": target_audience,
        "scope": claims["scope"],
        "act": claims.get("act", {}).get("sub", "token-exchange-service"),
    })
    
    return target_token
```

## الاعتبارات الأمنية

### التحقق من الرمز

خدمة تبادل الرموز يجب أن تتحقق من الرمز المصدر قبل إصدار رمز جديد:

- تحقق من التوقيع.
- تحقق من الانتهاء.
- تحقق من المصدر والجمهور.
- تأكد من أن الرمز لم يتم إلغاؤه.

### تضييق النطاقات

خدمة تبادل الرموز يجب أن تضيق النطاقات، لا توسعها أبدًا. إذا كان الرمز المصدر لديه نطاق `read`، يجب أن يكون الرمز الهدف لديه نطاق `read` أو مجموعة فرعية، أبدًا ليس `write`.

### تقييد الجمهور

جمهور الرمز الهدف يجب أن يُطلب صراحة ويُتحقق منه. خدمة تبادل الرموز لا يجب أن تصدر رموزًا لجمهور عشوائي.

### التحقق من سلسلة الممثل

خدمة تبادل الرموز يجب أن تتحقق من سلسلة الممثل لمنع إساءة الاستخدام:

- ارفض الرموز ذات سلاسل الممثل العميقة بشكل مفرط.
- تحقق من أن كل ممثل في السلسلة مخول للتفويض.

### ربط الرمز

تبادل الرموز يجب أن يحافظ على ربط الرمز (DPoP، mTLS) من الرمز المصدر إلى الرمز الهدف. إذا كان الرمز المصدر مربوطًا باتصال TLS، يجب أن يكون الرمز الهدف مربوطًا بنفس الاتصال.

## تبادل الرموز مقابل تحديث الرمز

| الجانب | تبادل الرموز | تحديث الرمز |
|---|---|---|
| الغرض | تبادل رمز بآخر | تجديد رمز منتهي |
| نوع المنح | `token-exchange` | `refresh_token` |
| المدخل | أي نوع رمز | رمز تحديث |
| المخرج | رمز جديد بجمهور/نطاق مختلف | رمز وصول جديد بنفس الجمهور/النطاق |
| الممثل | قد يضيف مطالبة ممثل | لا مطالبة ممثل |
| حالة الاستخدام | تفويض عبر الخدمات | استمرار الجلسة |

## ما تعلمه هذه الصفحة

- تبادل الرموز يتيح التفويض عبر الخدمات: خدمة يمكنها تبادل رمز المستخدم برمز للوصول إلى خدمة لاحقة.
- التفويض يحافظ على هوية المستخدم؛ انتحال الهوية لا يفعل. فضّل التفويض للتدقيق.
- سلاسل الممثل تُظهر مسار التفويض الكامل: كل مطالبة `act` تمثل خدمة في السلسلة.
- تبادل الرموز عبر السحابة يتيح اتحاد الهوية متعدد السحابة: رمز من سحابة واحدة يمكن تبادله برمز من سحابة أخرى.
- الأمان أمر بالغ الأهمية: تحقق من الرمز المصدر، ضيق النطاقات، قيّد الجمهور، وحافظ على ربط الرمز.
