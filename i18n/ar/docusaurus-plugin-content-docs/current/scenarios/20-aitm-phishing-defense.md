# الاستجابة لحوادث التصيد الاحتيالي بالوسيط المعادي (AiTM)

يمثل التصيد الاحتيالي القائم على الخادم الوكيل العكسي (Adversary-in-the-Middle - AiTM) التهديد الأكثر خطورة وتطوراً الذي يواجه بيئات الهوية المؤسسية اليوم. ففي حين كان التصيد التقليدي يقتصر على سرقة كلمات المرور، تتمركز أطر عمل AiTM (مثل **Evilginx** و**Muraena**) كخادم وسيط شفاف يعترض حركة المرور بين الضحية ومزود الهوية الحقيقي (مثل Microsoft Entra ID أو Okta).

عندما يدخل الموظف اسم المستخدم وكلمة المرور ويُكمل تحقق المصادقة المتعددة (عبر تطبيق الهاتف Authenticator أو الرسائل النصية SMS أو رموز TOTP)، يعترض الخادم الوسيط **كعكة الجلسة الموثقة (Session Cookie)** مثل `ESTSAUTH` ورمز التحديث `refresh_token`. يحقن المهاجم هذه الكعكات في متصفحه فوراً، ليحصل على جلسة دخول نشطة وموثقة بالكامل تتجاوز كلمات المرور والمصادقة الثنائية التقليدية كلياً دون إطلاق أي إنذار بفشل تسجيل الدخول.

## 2. إشارات الإنذار ورصد الهجوم (Detection Signals)

يجب على مركز العمليات الأمنية (SOC) مراقبة المؤشرات التحذيرية (IoCs) التالية في سجلات التدقيق:

| مصدر الإشارة | الحقل وسجل المراقبة | المؤشر الدال على الاختراق (IoC) |
|---|---|---|
| **سجلات تسجيل دخول Entra ID** | `RiskEventTypes` | رصد أحداث `anomalousToken` (رمز غير طبيعي)، `tokenIssuerAnomaly`، و`unfamiliarFeatures`. |
| **سجلات الوكيل والعميل (UserAgent)** | `ClientAppUsed` و`UserAgent` | تحول مفاجئ من متصفح Chrome/Edge المكتبي للموظف إلى استدعاء عبر مكتبة Python أو curl أو متصفح خفي (Headless) في غضون 60 ثانية من تسجيل الدخول. |
| **شذوذ الشبكة وعناوين IP** | عدم تطابق مزودي الخدمة ISP | حدوث المصادقة الأولى من مزود إنترنت محلي شرعي (مثل الاتصالات السعودية STC أو المصرية للاتصالات)، ثم استخدام كعكة الجلسة بعد 30 ثانية من عنوان IP تابع لشبكة استضافة سحابية (مثل DigitalOcean أو AWS أو Linode). |
| **ادعاءات امتثال الأجهزة** | `DeviceDetail.isCompliant` | سجل تسجيل الدخول يوضح جهازاً ممتثلاً ومعتمداً، ولكن استدعاءات APIs التالية بالرمز المسروق تخلو تماماً من معرف الجهاز (`deviceId == null`). |

## 3. خطة الاحتواء الفوري (Immediate Containment)

عند تأكيد وقوع حادث اختطاف جلسة عبر AiTM، تُنفذ الخطوات التالية بتسلسل زمني صارم:

### الخطوة 1: الإلغاء الفوري لكافة الجلسات ورموز التحديث
إغلاق المتصفح لا يلغي الرموز المسروقة. يجب على المستجيب للحادث إبطال كافة الجلسات ورموز Refresh Tokens برمجياً عبر الدليل السحابي:

```powershell
# استخدام Microsoft Graph PowerShell لإسقاط كافة جلسات المستخدم فوراً
Import-Module Microsoft.Graph.Users
Revoke-MgUserSignInSession -UserId "user@enterprise.com"
```

وفي بيئات Okta عبر استدعاء API المباشر:
```bash
curl -X DELETE "https://enterprise.okta.com/api/v1/users/{userId}/sessions" \
  -H "Authorization: SSWS ${OKTA_API_TOKEN}"
```

### الخطوة 2: تفعيل التقييم المستمر للوصول (Continuous Access Evaluation - CAE)
التأكد من إرسال مزود الهوية إشارات إبطال فورية لحظية إلى الخدمات السحابية المرتبطة (مثل Exchange Online وSharePoint) لإسقاط رموز الوصول المخزنة مؤقتاً دون انتظار انقضاء مدة الـ 60 دقيقة لعمر رمز JWT.

### الخطوة 3: تدوير كلمة المرور وإلغاء كلمات مرور التطبيقات
إعادة تعيين كلمة مرور الحساب فوراً؛ فرغم أن كلمة المرور لم تكن وسيلة التجاوز الأساسية، إلا أن المهاجم استخلصها بنص صريح أثناء مرورها عبر الخادم الوسيط.

### الخطوة 4: التفتيش الجنائي عن آليات البقاء والرسوخ (Persistence)
يسارع المهاجمون فور اختطاف الجلسة إلى زرع آليات تمكنهم من البقاء حتى بعد إلغاء الجلسة:
- **تسجيل وسائل MFA جديدة:** فحص سجلات Entra ID للبحث عن حدث `User registered security info` في الدقائق العشر التالية للاختراق (غالباً ما يسجل المهاجم تطبيق Authenticator أو مفتاح FIDO خاصاً به).
- **قواعد إعادة توجيه البريد:** فحص علبة الوارد لكشف قواعد التوجيه الخفية التي تنقل الرسائل الحاوية على كلمات مثل "تحويل"، "فاتورة"، "أمان" إلى بريد خارجي.
- **تخويل تطبيقات OAuth مشبوهة:** مراجعة أذونات التطبيقات للتأكد من عدم منح الموافقة (Consent) لتطبيقات طرف ثالث ضارة نيابة عن المستخدم.

## 4. الوقاية الجذرية: المعمارية المقاومة للتصيد الاحتيالي

لا يمكن تهيئة وسائل المصادقة الثنائية التقليدية (SMS أو Push Notifications) لتصمد أمام هجمات الخادم الوكيل العكسي. وللقضاء الجذري على هذه الثغرة، يجب فرض الضوابط التالية:

1. **مفاتيح الأمان العتادية FIDO2 ومفاتيح المرور (Passkeys):** يضمن مبدأ **الربط التشفيري بالنطاق (Cryptographic Origin Binding)** رفض المتصفح ومفتاح الأمان توقيع أي تحدٍ أمني إذا كان النطاق الظاهر في شريط العناوين هو `login.microsoft.phishingsite.net` بدلاً من النطاق الشرعي.
2. **المصادقة المعتمدة على الشهادات الرقمية (CBA):** فرض التشفير المتبادل (Mutual TLS) عبر البطاقات الذكية أو مفاتيح PIV العتادية. تتم المصادقة هنا مباشرة على مستوى طبقة النقل (TLS Layer)، ويستحيل على أي وكيل HTTP اعتسافها أو اعتراضها.
3. **الوصول المشروط المشترط لامتثال الجهاز (Compliant Device Conditional Access):** اشتراط صدور طلبات المصادقة حصرياً من أجهزة مسجلة في نظام الإدارة (Intune) ومحمية بشريحة عتادية (TPM). وحتى لو نجح المهاجم في سرقة بيانات الدخول، فإن خادمه السحابي يفتقر إلى شهادة الجهاز العتادية الموثوقة.
